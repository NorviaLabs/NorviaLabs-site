Building Forge.

The problem

Most terminal coding agents optimise one loop: prompt in, patch out. Real engineering work is wider than that. You read code, edit some of it yourself, hand other parts to an agent, run commands, review diffs, check behaviour, switch tasks, and come back later.

Once the agent can run commands, a second problem appears: how do you let it work without approving every keystroke, and without trusting it with your whole machine? Most tools answer by asking you more often. Forge's answer is to make the safe case the default case, enforced by the operating system.

What Forge is

One keyboard-driven terminal workspace in which the agent is part of the environment rather than the whole environment:

  • Agent conversations, a file explorer, a Vim-style editor, an interactive shell, diffs, diagnostics and approvals, in one TUI.
  • Several independent sessions at once. Managed sessions each get their own durable state and an isolated Git worktree, so one can keep working while you direct another.
  • Agent shell commands run inside an OS sandbox confined to the workspace, with network access denied by default and opened per host.
  • Transcripts, task state and unfinished work are kept in a local SQLite journal, so a session survives a crash or restart.
  • Provider sign-in and per-session model choice across OpenAI, Anthropic, xAI, Codex, OpenCode and local Ollama models, plus MCP servers for extra tools.

Decisions

1. Safety comes from the operating system, not from parsing commands

The early design tried to decide which shell commands were safe by reading them. That approach fails open: any command the parser misreads gets through. In August 2026 we rewrote the permission model around one falsifiable goal:

“Zero prompts for reads and in-workspace writes. Prompts only for network egress to a non-allowlisted domain, for escaping the workspace, and on platforms where the sandbox is unavailable.”

Forge permission model spec, agreed 17 Aug 2026

Agent commands are now confined at spawn: Seatbelt on macOS, bubblewrap on Linux, and the Linux path under WSL2 on Windows. Network access goes through a domain-filtered egress proxy over a Unix socket, and denials explain themselves. The reference design was a sandbox plus an approval policy, deliberately with no model in the approval path, because a tool that runs on several providers can't depend on any one provider's classifier. With enforcement in place, we deleted the roughly 1,650-line read-only command parser.

2. Declining a hardening step, and writing down why

The obvious next step on Linux was a seccomp filter to block Unix-domain sockets. It turned out the filter would have cut Forge's own egress relay, which runs inside the sandbox and needs the same socket call. Doing it properly would mean redesigning the relay around a passed-in file descriptor.

So we closed it as “will not do” on 18 Aug 2026 and recorded the reasoning. The risk it addressed is covered where it can be checked: /run and /tmp are masked inside the sandbox, the abstract socket namespace follows the replaced network namespace, and a test asserts that a confined command can reach sockets in the workspace but not host sockets. On macOS the sandbox already denies those connects outright. The note also says when to revisit it.

3. Sessions are journalled, and never resume work on their own

Every session writes to a local SQLite event journal, with a replay checkpoint every 256 events, so a session can be rebuilt after a crash. After a crash, Forge restores state but does not restart work that was in flight: stale “running” tasks are reconciled, and a failed turn recovers without replaying the step that poisoned it. An agent that silently resumes a half-finished command after a restart is a worse failure than one that waits for you.

4. Governance sits in the tool path

Every tool call passes through forge-governance before it runs: an access-control policy, a human-approval policy for tools the sandbox can't confine (MCP servers are separate processes, so they still ask), and pattern rules you can add for a session or permanently. Each decision produces an audit event recording the session, tool, redacted arguments, decision, policy and duration. This is the working seed of Guard and Audit.

What's still open

  • Forge is pre-release software. The README asks you to review every approval prompt and to start in a disposable or backed-up repository.
  • There is no native Windows build; Windows runs Forge under WSL2.
  • On Linux the sandbox needs bubblewrap and socat. Without them Forge still runs, but asks before every command.
  • The Unix-socket filter on Linux is deferred until the egress relay is restructured.

Everything on this page comes from the Forge repository: its README, architecture notes, design documents and commit history. If something here and the repository disagree, the repository is right.
